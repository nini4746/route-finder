# docs/design-docs/

Design documents capture the **invariants and rationale** behind the project — the things that survive across refactors.

## What lives here

- `core-beliefs.md` — one numbered belief per constraint in `initial-seed.yaml`. Read this before proposing a design change.

## What should NOT live here

- Work plans, status updates, or task tracking — those go to `docs/exec-plans/`.
- Product specifications — those go to `docs/product-specs/`.
- API references or third-party tool docs — those go to `docs/references/`.

## When to add a file

- A new cross-cutting design rule that does not fit in `core-beliefs.md` (rare; most rules should be a belief).
- A lazy design document the project actually needs — see `references/templates.md` in the harness-spec skill for the catalog (FRONTEND.md, SECURITY.md, RELIABILITY.md, etc.). Lazy docs are not regenerated by `--rerender`.

## Regeneration

`core-beliefs.md` is regenerated by `/harness-spec --rerender`. Hand-edits will be overwritten — to change a belief, edit `initial-seed.yaml > constraints` and rerender.
