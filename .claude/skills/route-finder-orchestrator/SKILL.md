# route-finder orchestrator

## Skill Overview

This skill is the entry point for the **route-finder** project: a macOS pygame
desktop program that generates random perfect mazes (up to 1000x1000 cells)
with the DFS Backtracker algorithm and visualizes six pathfinding algorithms
finding a path from a randomly chosen point A to point B, coloring every
visited cell as the search progresses. The canonical spec lives at
`docs/product-specs/initial-seed.yaml`.

The team is a `producer_reviewer`-pattern `team` of two agents — `builder`
(produces code drafts and a self-check against the acceptance criteria) and
`reviewer` (verifies acceptance criteria, especially perfect-maze invariants
and pathfinding correctness). Both were generated by `harness-build` from
`initial-seed.yaml`. To change the team shape, edit
`initial-seed.yaml.team_architecture` and re-run `/harness-build --refresh`;
do not hand-edit this orchestrator's structure.

Trigger phrases include: "add an algorithm to route-finder", "speed up the
maze generation", "fix the perfect-maze invariant", "refine the sidebar",
"based on the previous review, redo the pathfinding refactor". Does NOT
trigger on unrelated pygame tutorials or generic maze-algorithm questions
that are not about modifying this project.

## Workflow

### Phase 0: Context check

Before any agent invocation:

```
if _workspace/ exists and contains draft_v<N>.md or review_v<N>.md:
  if the user request names specific agents to re-invoke (e.g., "re-run
      reviewer only on the current draft"):
    mode = partial_rerun
  elif the user provides a new feature request unrelated to the prior draft:
    mode = fresh_run
    move _workspace/ to _workspace_prev_<timestamp>/
  else:
    mode = resume
    ask user: "Resume from where? [continue | fresh | partial]"
else:
  mode = initial_run
  mkdir _workspace/
```

In all modes, write the current request to `_workspace/request.md` before
invoking any agent.

### Phase 1: builder draft (producer)

Invoke `builder` with the user's request from `_workspace/request.md` (and,
if `mode == initial_run`, no prior review). `builder` writes
`_workspace/draft_v1.md` containing a change summary, the code, and a
self-check against the targeted acceptance criteria (AC1..AC12).

**Validation hook**: confirm `_workspace/draft_v1.md` exists and is
non-empty before proceeding.

### Phase 2: reviewer critique

Invoke `reviewer` against `_workspace/draft_v<N>.md` (the latest draft).
`reviewer` writes `_workspace/review_v<N>.md` with `PASS` or `FAIL`, a
per-AC table, and concrete amendments for each `FAIL` item.

**Validation hook**: confirm `_workspace/review_v<N>.md` exists and has a
verdict line.

### Phase 3: iterate or accept

```
if review_v<N> verdict == PASS:
  goto Phase 4
elif iter < 3:
  invoke builder again; it reads draft_v<N>.md + review_v<N>.md and writes
      draft_v<N+1>.md
  goto Phase 2 with N <- N+1
else:
  # iteration budget exhausted
  accept latest draft, note "iteration budget exhausted" in the final
      deliverable, surface the still-failing items to the user
  goto Phase 4
```

The iteration cap is **3** (matches the producer_reviewer pattern default).

### Phase 4: final synthesis

The deliverable is the accepted `draft_v<N>.md` plus its `review_v<N>.md`,
plus the actual code changes already applied to the project tree by
`builder`. The orchestrator prints a one-paragraph summary naming:
- the iteration number reached
- which acceptance criteria were satisfied
- which acceptance criteria (if any) remain not met and why
- next-step suggestions (e.g., "re-run with stricter input on AC7")

## Data Flow

Agents coordinate via **files** under `_workspace/`. The orchestrator
creates `_workspace/` on `initial_run` and writes `_workspace/request.md`
with the user's request. `builder` writes `_workspace/draft_v<N>.md`.
`reviewer` writes `_workspace/review_v<N>.md`. Both agents may read each
other's most recent file plus `docs/product-specs/initial-seed.yaml` and
the actual project source. Each agent reads only files written by the
prior phase (no mid-run state).

`files` is the producer_reviewer pattern's preferred data-flow primitive
for this team size — the iteration history is auditable on disk, and the
review trail survives session restarts.

## Error Handling

Pattern defaults (from `producer_reviewer` in the harness patterns
reference):

- On `builder` failure: 1 retry. If retry fails, abort the chain and surface
  the partial `_workspace/draft_v<N>.partial.md`. Do not invoke `reviewer`
  on a partial draft.
- On `reviewer` failure: 1 retry. If retry fails, accept the latest draft
  and warn the user that the review was not completed.
- Iteration cap: 3. After the cap, accept the latest draft and note
  "iteration budget exhausted" in the deliverable.

Universal rules:

- 1-retry policy per agent invocation. No second retry — escalate or accept
  partial.
- Partial results are surfaced with the explicit `.partial.md` suffix;
  never silently dropped.
- Conflicting outputs across iterations are preserved (each `draft_v<N>` and
  `review_v<N>` stays on disk); never collapsed into a single file.

## Re-invocation Support

- **Initial run** — no prior `_workspace/`. Run Phases 1–4 from scratch.
  Trigger language: any first-time domain request (e.g., "add Bidirectional
  BFS to route-finder").
- **Partial rerun** — user names specific agent(s) to re-invoke; orchestrator
  skips others and reuses their prior output. For this 2-agent team the
  typical partial is "re-run reviewer only on the current draft" (e.g., after
  the spec changed but the code did not).
  Trigger language: "re-run reviewer only", "just re-review", "re-run the
  builder with new input".
- **Fresh run** — user provides a new, unrelated request. Orchestrator moves
  `_workspace/` to `_workspace_prev_<timestamp>/`, recreates `_workspace/`,
  runs the full workflow on the new request.
  Trigger language: "start fresh", "new feature: ...", "ignore the prior
  draft".
- **Resume** — orchestrator detects ambiguity and asks the user
  `Resume from where? [continue | fresh | partial]`.
  Trigger language: any re-invocation where the user's intent vs. prior
  `_workspace/` is unclear.

## Test Scenarios

### Happy path

User asks: "Add Bidirectional BFS to route-finder and wire it to the `6`
key and the sidebar."

1. Phase 0: `_workspace/` does not exist → `mode = initial_run`. Orchestrator
   creates `_workspace/` and writes `request.md`.
2. Phase 1: `builder` writes `_workspace/draft_v1.md` containing the new
   `bibfs.py` implementation behind the common `step()` interface, the
   sidebar wiring, the `6`-key shortcut, and a self-check claiming AC5,
   AC6, AC7 are addressed.
3. Phase 2: `reviewer` writes `_workspace/review_v1.md` with `PASS` because
   the per-AC table shows AC5, AC6, AC7 met and no other AC affected.
4. Phase 3: verdict is `PASS` → jump to Phase 4.
5. Phase 4: deliverable is `draft_v1.md` + `review_v1.md` + the applied code
   changes. One-paragraph summary tells the user AC5/6/7 are satisfied.

### Failure path

User asks: "Speed up DFS Backtracker maze generation."

1. Phase 0: `initial_run`. `_workspace/` created, `request.md` written.
2. Phase 1: `builder` writes `_workspace/draft_v1.md` that removes the
   step-by-step animation hook to make generation finish in one tick.
3. Phase 2: `reviewer` writes `_workspace/review_v1.md` with `FAIL`. The
   per-AC table flags AC4 ("animates the generation at the current speed
   slider value") and the constraint "maze generation animates step-by-step
   at the speed configured by the speed slider". Concrete amendment: keep
   the step generator but allow batching `k` steps per frame, where `k`
   scales with the speed slider.
4. Phase 3: verdict is `FAIL`, `iter = 1 < 3` → invoke `builder` again.
   `builder` reads `draft_v1.md` + `review_v1.md` and writes `draft_v2.md`
   with the batching approach.
5. Phase 2 (again): `reviewer` writes `review_v2.md` with `PASS`.
6. Phase 4: deliverable is `draft_v2.md` + `review_v2.md` + the applied code
   changes. Summary names AC4 as satisfied via the batching fix from the
   review feedback.
